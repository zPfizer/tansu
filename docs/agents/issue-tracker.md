# Issue tracker: GitHub

Specs and tickets of this repo are GitHub issues in `zPfizer/tansu` (remote `origin`). Use the `gh` CLI for all operations. `gh` finds the repo from `git remote -v`.

`.scratch/` is local and gitignored. It holds temporary job files and the old read-only ticket archive. The old archive also remains in git history. GitHub and CI do not require these local files. An open ticket has one place: its issue.

## Issue and PR rule

Source: Levent 18.10: "Issue ve PR kuralını onaylıyorum." This section owns the full rule.

1. **Direct to master, no issue or PR:** Use this path only for a clear, harmless document fix: spelling, format, a broken link, or a wrong fact line. If unsure, use the PR path. This direct path is a TANSU choice. Small-team trunk guidance permits direct commits ([S12](https://trunkbaseddevelopment.com/)).
2. **PR without an issue:** Use this path for a larger document fix that needs no decision. Put the reason in a separate body line: `Issue yok: <reason>`. Use the title `Belge · <short title>`. CI accepts this path only when every changed file is `*.md`, outside `.claude/`, `.github/`, `docs/kurallar/`, and `docs/agents/`. It also excludes `docs/TASARIM.md`, `docs/KURALLAR.md`, `CODING_STANDARDS.md`, `DEFINITION_OF_DONE.md`, and `GLOSSARY.md` because they own rules. Files named `AGENTS.md` or `CLAUDE.md` at any level are excluded because they carry agent rules. A clear typo in an excluded file can still use item 1. An empty or unknown file list fails this check. An issue exemption for document fixes also exists in [S4](https://devguide.python.org/getting-started/pull-request-lifecycle/) and [S6](https://docs.djangoproject.com/en/dev/internals/contributing/writing-code/submitting-patches/).
3. **Issue + PR:** Use this path for code, tests, CI, hooks, settings, refactoring that keeps behavior, and any change of a rule's meaning. Use a branch for the issue. The existing `Closes #N` and `#<N> · <short title>` checks still apply. Reviewed refactoring is part of [S11](https://google.github.io/eng-practices/review/developer/small-cls.html). GitHub documents issue links in [S3](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue).
4. **Issue only:** Use this path for deferred work. Never defer a small document error. Immediate correction is a TANSU choice. Issues can track future work ([S2](https://docs.github.com/en/issues/tracking-your-work-with-issues/learning-about-issues/about-issues)).
5. **Direct push owner and CI:** Only Claude pushes directly to master. Claude says "done" only after green CI. On red CI, Claude reverts at once. This actor restriction and the immediate revert are TANSU choices. Trunk guidance requires a green build and fast recovery ([S13](https://trunkbaseddevelopment.com/committing-straight-to-the-trunk/)).

## Conventions

- **Create an issue**: `gh issue create --title "..." --body-file <file> --label needs-triage --milestone "<name>"`. The issue template `.github/ISSUE_TEMPLATE/is.md` sets the layout.
- **Read an issue**: `gh issue view <number> --json number,title,body,labels,assignees,state,comments`.
- **List issues**: `gh issue list --state open --json number,title,labels,assignees` with `--label` and `--state` filters.
- **Comment**: `gh issue comment <number> --body "..."`.
- **Labels**: `gh issue edit <number> --add-label "..."` / `--remove-label "..."`.
- **Close**: `gh issue close <number> --comment "..."`.
- **Spec**: one issue, title `Spec: <name>`. The tickets name it in a `Parent: #N` line.
- **Issue body**: follow "Issue body" below. Each issue also has one triage label and a milestone. Every open issue belongs to one open milestone. Name each open milestone `v0.<n>.0 — <short Turkish benefit>`, in work order. Its description states the benefit, then `Sıra: #a, #b, #c`. Source: Levent 18.10.
- **Branch**: for the issue + PR path, use `<N>-<ad>`, made by `gh issue develop <N> --name <N>-<ad> --base master` (`tansu-yeni-is` "Branch"). For a PR without an issue, use `belge-<ad>`.
- **PR**: use the body and title forms in "Issue and PR rule". GitHub shares one number sequence for issues and PRs. A merge with `Closes #N` closes that issue.

## Issue body

Source: Levent 19.10: "Açtığımız issue'lar çünkü çok detaylı değil. Yani ben okuyunca bile anlamıyorum." / "Tüm issue'lar triage skill ile yazılsın." / "Bundan sonra da böyle olsun yani. Bu genel bir kural."

Before any flow creates an issue, write its body with `mattpocock-skills:triage`.
Follow that skill's bundled reference, AGENT-BRIEF.md, for the agent brief.
Use `.github/ISSUE_TEMPLATE/is.md` for the layout.
Write the body in this order:

1. Start with `> *This was generated by AI during triage.*`.
2. Add `## Levent için`. Write 4–8 sentences in plain Turkish. Include one example. Use no code names or paths in this section.
3. Keep the three bold fields: `**Amaç:**` (what to build), `**Kaynak:**` (fact sources), then `**Bitti koşulu:**` (completion condition).
4. Add `## Ajan brifi`. Include category, summary, current behavior, desired behavior, key interfaces, testable acceptance criteria, scope exclusions, and tests.
5. End with `**Bağlı:**` and the related issues or prerequisites. If none exist, write `yok`.

Describe behavior and interface contracts in the brief. Use types, signatures, or configuration shapes when needed.
Follow its brief rules: omit file paths, line numbers, and implementation recipes from the brief.
Keep acceptance criteria independently testable. State the affected tests to run.
`triage-labels.md` owns the state labels. The category in the brief is `bug` or `enhancement`.

## State of a ticket

An open ticket has exactly one triage-role label (`triage-labels.md` owns the label strings). The state comes from the label, the assignee, the PR link, and the issue state:

| Old `Status:` value | GitHub |
|---|---|
| a triage role string | the label of that role (`triage-labels.md`) |
| `claimed` | an assignee: `gh issue edit <n> --add-assignee @me` (the first write before any work). The role label stays. |
| `in-review` | an open PR with `Closes #N` in its body. The issue stays open. |
| `done (PR #N, hash)` | the issue is closed by the merge of the PR. |
| `done (kısa not)` | the issue is closed by hand with `gh issue close <n> --comment "<short note>"`. The comment says what is delivered and what moved elsewhere. |
| `resolved` | the issue is closed after the answer comment (a wayfinder child). |

A ticket is closed when the issue state is closed. A ticket is claimed when it has an assignee.

## Status field

This section keeps the old `Status:` contract. It describes only the local, read-only ticket archive under `.scratch/` and its copies in git history. GitHub and CI do not require the archive. New work does not use this contract. `triage-labels.md` owns only the role strings. The old tickets write it as `**Status:** <value>`. The value is one of:

- A triage role string from `triage-labels.md`: the ticket waits for triage or for work.
- `claimed`: work started. Set it and save before any work.
- `in-review`: the work is on its branch and waits for the independent audit or the PR review.
- `done (PR #N, hash)`: merged. The parentheses name the PR and the merge commit.
- `done (kısa not)`: delivered, not merged. The parentheses hold one short note: what is delivered and what moved elsewhere; the branch name is optional (example: ticket 06 of `belge-hizasi`). When the merge happens, the value becomes `done (PR #N, hash)`.
- `resolved`: the closing value of a wayfinder child ticket (see "Wayfinding operations").
- `done`: the legacy value of the closed tickets in the local, read-only `.scratch/arsiv/tansu-mvp/issues/` archive (before 14.10), also available in git history.

A ticket is closed when its value starts with `done` or `resolved`. (bilet 05, 14.10)

## Blocking

A `Blocked by: #N, #N` line near the top of the issue body. A ticket is unblocked when every issue it lists is closed. Do not use the native dependency feature of GitHub. One format keeps the check simple.

## When a skill says "publish to the issue tracker"

Create a GitHub issue.

## When a skill says "fetch the relevant ticket"

Read the issue as in **Read an issue**. The user normally passes the issue number.

## Wayfinding operations

Used by `mattpocock-skills:wayfinder`. The **map** is one issue. The **children** are issues.

- **Map**: one issue with the label `wayfinder:map` (create the label at first use: `gh label create wayfinder:map`). The body holds the Notes / Decisions-so-far / Fog text.
- **Child ticket**: an issue with a `Parent: #<map>` line and a `Type:` line (`research`/`prototype`/`grilling`/`task`) at the top of the body. The question is in the body.
- **Blocking**: the `Blocked by:` line above.
- **Frontier**: the open children of the map (`gh issue list --state open --search "Parent: #<map> in:body"`) without an assignee and without an open blocker. The first by number wins.
- **Claim**: `gh issue edit <n> --add-assignee @me` before any work.
- **Resolve**: `gh issue comment <n> --body "<answer>"`, then `gh issue close <n>`. Then append a context pointer (gist and link) to the Decisions-so-far in the map issue.
